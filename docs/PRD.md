## 1. 背景

### 1.1 问题

几个人一起点麦当劳时，「怎么点最划算」是一个高频、但很难算清的小决策：

- **组合太多**：一家门店有 100 多个餐品、60 多个套餐，套餐里又含主食、小食、饮料，人工几乎不可能穷举。
- **价格有陷阱**：部分套餐标的是「随单购麦金卡优惠」价，不另买卡就拿不到。例如巨无霸四件套菜单显示 32 元，实际要 58.5 元。
- **券用不上**：账户里的券、门店可用券需要逐张试算，才知道能不能用、能省多少。
- **让大模型凑单不可靠**：容易算错价、漏组合、多点冗余餐品，或者编造优惠。

### 1.2 机会

麦当劳开放了官方 MCP Server（35 个工具），可以实时读取门店菜单、套餐组成、营养数据、优惠券，并用官方 `calculate-price` 计算到手价，还能直接下单。把这些能力和优化算法、语音交互结合起来，可以把「几个人、多少钱、怎么点」变成一句话就能得到答案的体验。

### 1.3 目标

| 目标 | 衡量方式 |
|---|---|
| 给出可信的最优方案 | 每个方案的价格都经过麦当劳 `calculate-price` 实时校验，展示价即到手价 |
| 足够快 | 同一门店当天再次生成方案 ≤ 5 秒（实测约 2.5–4 秒） |
| 能直接完成点餐 | 从说出需求到拿到支付入口，全程在一个页面内完成 |
| 安全可控 | 任何写操作（下单、领券）都必须由用户明确确认，AI 无法自行触发 |
| 参赛合规 | 满足大赛对仓库文件、真实调用 MCP、无敏感信息的要求 |

## 2. 目标用户与场景

### 2.1 用户画像

| 用户 | 特征 | 核心诉求 |
|---|---|---|
| 同事 / 同学聚餐的组织者 | 要给 3–10 个人点餐，有总预算 | 每人都吃上完整一份，总价不超预算 |
| 精打细算的麦当劳常客 | 月底预算紧张，熟悉套餐但懒得算 | 用最少的钱吃饱 |
| 想吃顿好的打工人 | 只关心「这些钱怎么吃最饱」 | 一个直接的答案，不想比价 |
| 双手不方便操作的用户 | 走路、开车前、做家务时 | 张嘴就能点 |

### 2.2 典型场景

1. **办公室拼单**：「三个人一百块，到店自取，上海人民广场」→ 三套方案 → 「就要第三个，外带」→ 屏幕确认 → 去支付。
2. **在家点外送**：「两个人八十块，送到家，不吃牛肉不吃辣」→ 方案自动计入配送费、打包费，并排除牛肉和辣味餐品。
3. **Agent 调用**：在 WorkBuddy / Claude Code 等客户端中，通过 Skill 让 AI 助手按规范完成凑单。

## 3. 产品范围

### 3.1 产品形态

| 形态 | 入口 | 适合谁 |
|---|---|---|
| 语音点餐网页（主推） | `npm run voice`（电脑）/ `npm run voice -- --lan`（手机） | 普通用户 |
| 命令行工具 CLI | `node src/cli.js plan …` | 开发者、脚本 |
| AI Skill | `skills/mcd-coudan/SKILL.md` | WorkBuddy 等 Agent 客户端 |

三种形态共用同一套凑单引擎（`src/planner.js`、`src/optimizer.js`、`src/catalog.js`）。

### 3.2 本期范围（已实现）

- 到店自取、麦乐送两种场景的凑单
- 最省钱 / 吃最饱 / 最超值三种策略
- 搭配要求、忌口、排除餐品、口味多样化
- 门店可用券自动试算并参与组合
- 下单（需确认）、麦麦省领券（需确认）、查询订单状态
- 实时全双工语音对话，电脑和手机浏览器都可使用
- 「去支付」唤起麦当劳 App 收银台

### 3.3 不在本期范围

- 自建支付或直接唤起支付宝 / 微信支付（麦当劳 MCP 不提供支付接口，见 §6.3）
- 套餐内换品（如可乐换雪碧、薯条升级）和餐品特制选项
- 得来速（beType=5）、企业团餐（beType=6）、预约点餐
- 用户账户体系、多用户共享服务（当前为单用户、本机部署）
- 公网部署（当前仅本机 / 局域网）

## 4. 功能需求

优先级：P0 必须有，P1 应该有，P2 可以有。

### 4.1 凑单引擎

#### F1 选择门店（P0）

| 场景 | 规则 |
|---|---|
| 到店自取 | 用户提供城市 + 附近地点，调用 `query-nearby-stores`（`searchType=2`），选距离最近且营业中的门店；也支持直接指定门店编号 |
| 麦乐送 | 读取账户配送地址（默认第一个，可指定），调用 `delivery-query-stores` 选可配送且营业中的门店 |
| 异常 | 没找到营业门店、没有配送地址、地址不在配送范围时，给出明确提示 |

#### F2 餐品画像（P0）

把菜单整理成可计算的「餐品画像」：

- **份数**：每个餐品能满足几份主食 / 小食 / 饮料。套餐按 `query-meal-detail` 中每轮的默认选项（`isDefault=1`）计算。
- **分类规则**：名称含「堡、巨无霸、麦香鸡、麦香鱼、麦满分、卷、饭、三明治、帕尼尼」等算主食；可乐、咖啡、奶茶、果汁等算饮料；其余算小食。周边、玩具、会员卡、单独的酱料不参与凑单。
- **真实单价**：优惠类型为「随单购麦金卡 / 早餐卡优惠」的餐品，按原价计算。
- **热量**：取自 `list-nutrition-foods`，按名称模糊匹配；查不到时按品类保守估算（主食 450、小食 250、饮料 140 千卡）。
- **缓存**：套餐详情按「门店 + 场景 + 日期」缓存，当天重复使用不再请求。

#### F3 搭配与口味（P0）

| 参数 | 说明 | 默认 |
|---|---|---|
| 人数 | 1–20 人 | 必填 |
| 预算 | 总预算（元），外送含配送费、打包费 | 不限 |
| 每人小食 / 饮料 | 可分别关闭 | 都要 |
| 忌口 | 牛肉、猪肉、鱼、辣、咖啡 | 无 |
| 排除餐品 | 按名称关键词排除 | 无 |
| 口味多样 | 同一款餐品最多点人数的一半 | 关 |

#### F4 三种方案（P0）

| 方案 | 定义 | 同分时 |
|---|---|---|
| 💰 最省钱 | 满足每人份数要求，到手价最低 | 热量高者优先 |
| 🍗 吃最饱 | 预算内总热量最高 | 价格低者优先 |
| 🏷 最超值 | 「比单点省下的金额 ÷ 单点总价」比例最高 | 价格低者优先 |

规则：

- 用帕累托动态规划搜索：状态是已满足的（主食、小食、饮料）份数，保留价格、热量、优惠三个维度上互不支配的组合。
- 不加入「去掉也够吃」的冗余餐品，也不为了凑热量加入补不上缺口的餐品。
- 每种策略取前 3 名候选，逐个用 `calculate-price` 校验，按真实到手价重新排序，最终三种策略各选一个且互不重复。
- 超出预算的方案直接淘汰；凑不出方案时，提示提高预算、去掉小食或饮料、减少忌口。
- 「比单点省」= 菜单原价合计 − 到手商品价。

#### F5 优惠券（P1）

- 读取门店可用券（`query-store-coupons`），逐张用 `calculate-price` 带券试算，券后价更低的作为独立候选参与组合，每个券码只用一次。
- 麦麦省领券（`available-coupons` / `auto-bind-coupons`）：先预览，用户确认后才领取；领券后重新凑单会自动用上。

### 4.2 下单与支付

#### F6 下单（P0）

- 按选定方案调用 `create-order`，商品与校验价格时完全一致。
- 到店自取必须带取餐方式（堂食 / 外带等，取值来自 `calculate-price` 返回的 `takeWayList`，各门店不同，例如有的门店「外带」是店外取餐柜）；外送必须带配送地址，可选备注（≤ 50 字）。
- **确认门槛**：CLI 必须加 `--confirm`；语音网页必须在屏幕上点击「确认下单」。语音模型最多只能弹出确认卡片。
- **防重复**：同一张确认卡片只能下单一次。
- **时效**：方案生成超过 1 小时后不能下单，需要重新计算。

#### F7 支付（P0）

- `create-order` 返回的是麦当劳的扫码页（`scanToPay`），页面只是一张指向 `jumpToApp` 的二维码，手机上无法直接付款。
- **手机端**：「去支付」直接唤起麦当劳 App 的订单详情并打开收银台，用户可在收银台选择支付宝或微信支付。2 秒内未唤起成功时，退回麦当劳官方跳转页；在微信内置浏览器中直接打开官方跳转页。
- **电脑端**：显示官方跳转页的二维码，手机扫码即可拉起 App 付款。
- **前提**：手机已安装麦当劳 App，并用申请 MCP Token 的同一手机号登录。

#### F8 订单状态（P1）

用户问「付好了吗」「到哪了」时，调用 `query-order` 查询并播报最新状态。

### 4.3 语音点餐

#### F9 实时语音对话（P0）

- 接入豆包实时语音模型 3.0（Seeduplex，全双工），用户可以随时插话打断。
- 连接成功后主动问候：「你好，我是麦门凑单大师。告诉我几个人、多少预算，到店还是外送……」
- 信息不全时追问（人数、取餐方式、到店地点必问；预算没说问一句）；信息够了直接计算，不反复确认。
- 播报方案时只说门店、每套方案的序号、名称、到手价、人均和最大亮点；不逐个念餐品，用户问了再说。金额用口语，例如「五十六块三」。
- 不编造餐品、价格或优惠，一切以工具返回为准；弹出确认卡片后不能说「已经下单」。

#### F10 语音模型可调用的工具（P0）

| 工具 | 作用 | 是否写操作 |
|---|---|---|
| `make_plans` | 按人数、预算、取餐方式等生成三套方案，同时把方案卡片推送到页面 | 否 |
| `prepare_order` | 在页面上弹出下单确认卡片，可带取餐方式和备注 | 否 |
| `order_status` | 查询本次对话中已创建订单的状态 | 否 |

真正的下单（`create-order`）只能由页面上的「确认下单」按钮触发，不对语音模型开放。

#### F11 网页界面（P0）

- **通话区**：麦克风按钮（未连接 / 连接中 / 聆听 / 播报 / 静音五种状态，带音量动效）、状态提示、静音、「我说完了」（强制判停）、结束通话。
- **对话区**：用户识别文本（实时更新）与助手回复字幕。
- **方案卡片**：门店、人数与搭配、每套方案的价格、人均、省多少、热量、餐品明细与套餐组成、配送费和打包费，每张卡片有「选这个」按钮，可以不用语音、直接点选。
- **确认卡片**：门店、地址、餐品、取餐方式选择、到手价、真实下单提示，「再想想」/「确认下单」。
- **下单结果**：订单号、「去支付」、电脑端支付二维码、麦当劳返回的原始信息（可折叠）。
- **防回声开关**：「播报时不收音」默认开启，外放时避免把助手的声音录进去；戴耳机时可关闭，以便随时插话。
- 手机屏幕保持常亮（浏览器支持时）。

#### F12 手机访问（P0）

- `--lan` 启动时监听局域网，自动生成自签 HTTPS 证书（浏览器要求 HTTPS 才开放麦克风）。
- 自动选取真实局域网地址（192.168 / 10 / 172.16–31），排除代理软件的虚拟网卡（如 198.18.x）。
- 电脑页面显示手机扫码入口。

### 4.4 命令行与 Skill

#### F13 CLI（P0）

| 命令 | 作用 |
|---|---|
| `stores --city --near` | 查附近门店（不带参数查收藏门店） |
| `plan --people --budget [门店] [口味]` | 生成三套方案，`--json` 输出给 Agent |
| `order --pick N [--confirm] [--take-way] [--remark]` | 按上次方案下单，不加 `--confirm` 只预览 |
| `claim [--confirm]` | 麦麦省领券，不加 `--confirm` 只预览 |

#### F14 Skill（P0）

`SKILL.md` 规定 Agent 的标准流程：问清需求 → 生成方案（CLI 模式或纯 MCP 模式）→ 展示方案 → 用户明确确认后下单 → 给出支付入口。纯 MCP 模式下写明每一步该调用哪个工具、参数规则和价格注意事项。

## 5. 非功能需求

### 5.1 性能

| 指标 | 要求 | 实测 |
|---|---|---|
| 首次生成方案（无缓存） | ≤ 10 秒 | 约 8 秒，约 70 次 MCP 调用 |
| 同门店当天再次生成 | ≤ 5 秒 | 2.5–4.2 秒，十几次调用 |
| 语音首次响应 | 说完话后 1 秒内开始回复 | 识别完成后约 0.2 秒出首字 |
| MCP 限流 | 每 Token 每分钟 ≤ 600 次 | 远低于上限 |

### 5.2 安全与隐私

- **密钥只在服务端**：麦当劳 Token、火山 API Key 只存在本地 `.env` 或环境变量中，不下发到浏览器，不提交到仓库。
- **访问口令**：语音服务的 WebSocket 必须带访问口令（默认每次启动随机生成，可用 `VOICE_ACCESS_KEY` 固定）；电脑页面上的手机扫码地址只回答本机请求。
- **默认只监听本机**：只有显式加 `--lan` 才对局域网开放。
- **写操作双重门槛**：下单、领券都必须用户明确确认；语音模型无法触发写操作。
- **静态文件**：禁止路径穿越，只能访问 `web/` 目录。

### 5.3 兼容性

- Node.js ≥ 22（使用内置 WebSocket 客户端），零第三方依赖，不需要 `npm install`。
- 浏览器：支持 AudioWorklet 和 getUserMedia 的现代浏览器（Chrome、Edge、Safari、主流手机浏览器）。
- 页面适配手机竖屏与电脑宽屏（≥ 900px 时左右两栏），支持深色模式。
- 二维码库从 CDN 按需加载，加载失败不影响点餐。

### 5.4 可靠性

- 工具执行出错时，也要按原 `call_id` 把错误回传给语音模型，避免模型一直等待。
- 断开连接时先发送 `session.close` 再关闭上游连接。
- 麦当劳 MCP 返回 401（Token 无效）、429（限流）时给出明确提示。
- 个别套餐详情查询失败时按单品处理，不影响整体出方案。

## 6. 外部依赖

### 6.1 麦当劳 MCP

| 工具 | 用途 |
|---|---|
| `query-nearby-stores` | 到店门店 |
| `delivery-query-addresses` / `delivery-query-stores` | 外送地址与门店 |
| `query-meals` / `query-meal-detail` | 菜单与套餐组成 |
| `list-nutrition-foods` | 热量 |
| `query-store-coupons` | 门店可用券 |
| `calculate-price` | 券后价试算、方案到手价校验 |
| `available-coupons` / `auto-bind-coupons` | 麦麦省领券 |
| `create-order` / `query-order` | 下单与订单查询 |

### 6.2 豆包实时语音（火山引擎）

- 地址：`wss://openspeech.bytedance.com/api/v3/duplex/realtime/dialogue`，模型 `1.2.6.1`，鉴权头 `X-Api-Key`。
- 上行 16kHz / int16 / 单声道 PCM，每 20ms 一包；下行 24kHz PCM（`pcm_s16le`）。
- 通过 Function Calling 调用本地工具。

### 6.3 支付

麦当劳 MCP 不提供支付接口。唤起支付宝付款需要麦当劳商户签发的支付参数，本产品无法生成，因此支付统一交给麦当劳 App 收银台完成。

## 9. 风险与已知限制

| 风险 / 限制 | 影响 | 应对 |
|---|---|---|
| App 唤起链接来自麦当劳官方跳转页的代码，不是公开接口 | 麦当劳改版后可能失效 | 唤起失败 2 秒后自动退回官方跳转页 |
| 「播报时不收音」开启时，助手说话期间的语音会被丢弃 | 用户抢话时前半句丢失 | 模型会追问缺失信息；戴耳机时可关闭该开关，体验真正的插话 |
| 手机首次访问提示证书不受信任 | 多一步操作，部分用户可能困惑 | 页面和终端都给出「继续访问」的提示 |
| 服务只能在本机 / 局域网使用 | 不在同一 Wi-Fi 的手机无法使用 | 后续可考虑公网部署（需要账户体系，见 §10） |
| 访问链接等同于下单权限 | 链接外泄后他人可用账户下单 | 随机口令、默认只听本机；终端明确提示不要外传 |
| 豆包识别事件的部分字段与文档描述不一致 | 字幕显示异常 | 已按实测协议适配（识别 `delta` 为整句而非增量） |
| 下单成功后的语音播报未经真实会话验证 | 可能不播报 | 页面始终显示支付入口，不依赖播报 |
| 菜单、价格随门店和时间变化 | 方案过期 | 方案 1 小时内有效；所有价格实时校验 |
